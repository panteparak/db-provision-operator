# User Manual

Readers are platform engineers installing the operator and app teams writing
CRs. They know Kubernetes; they don't know this codebase. Write what they do
and what they will observe (status, conditions, events, Secrets), not how the
code is structured.

## Where things go

| Content | File |
|---|---|
| Install, first database end to end | `docs/getting-started/{installation,quickstart}.md` |
| One page per CRD (fields, status, examples, deletion) | `docs/user-guide/<crd>.md` |
| Cross-cutting features | `docs/user-guide/{drift-detection,deletion-protection}.md` |
| Engine-specific behavior/limits | `docs/engines/<engine>.md` |
| Runbooks, monitoring, troubleshooting, migrations | `docs/operations/*.md` |
| Larger scenario walkthroughs | `docs/examples/*.md` |
| Field-by-field API reference | `docs/api/reference.md` — generated by `make generate-api-docs`; link to it, don't duplicate it |

New page → add it to that directory's `.pages` nav.

## CRD page skeleton

Match the existing pages (`docs/user-guide/users.md` is the reference):

1. `# <Kind>` + one sentence: what it represents.
2. `## Overview` — minimal working YAML.
3. `## Spec Fields` — `### <field> (required|optional)` per top-level field;
   table of sub-fields (Field / Type / Required / Description); state default,
   immutability, and validation (take from `+kubebuilder:` markers in
   `api/v1alpha1/<kind>_types.go`).
4. `## Status` — phases and conditions the user will see, and what to do.
5. `## Examples` — realistic scenarios, each a complete applyable manifest.
6. `## Deletion` — protection, `deletion-policy`, force-delete/cascade flow.
7. Feature sections (rotation, drift, ownership…), then troubleshooting links.

## Workflow

1. Read the code for the behavior: `api/v1alpha1/<kind>_types.go` (fields,
   defaults, enums) and `internal/features/<kind>/` (what reconcile actually
   does, per engine in `internal/adapter/<engine>/`). Never document from
   memory or from another doc.
2. Find the existing section (`grep -rn '<field>' docs`) and update in place;
   one canonical explanation, link to it from elsewhere.
3. Write. For every claim ask "would a user notice if this were wrong?" — if
   yes it must be checked against code.
4. Validate examples: every field exists (`grep -n 'json:"<field>' api/v1alpha1/*.go`);
   if a cluster with CRDs is available, `kubectl apply --dry-run=server -f`.
5. Run the `docs-sync` skill's script and `make docs-build` (strict).
6. Diagrams: use the `operator-diagrams` skill.

## Style

- mkdocs-material: `!!! tip|info|warning|danger "Title"` admonitions; engine
  differences as tabs:

  ```markdown
  === "PostgreSQL"
      ...
  === "MySQL"
      ...
  ```

- Second person, present tense, imperative steps ("Apply the manifest").
- Show the command *and* the expected output/status for each step.
- Exact names in backticks: kinds, fields, annotations, condition reasons,
  make targets. Destructive actions (`force-delete`, `deletion-policy: Delete`)
  get a `!!! danger` block.
- No roadmap promises or internal function names in user pages
  (`docs/development/` is the place for contributor material).
